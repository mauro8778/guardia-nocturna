1. CONTEXTO ARQUITECTÓNICO (ECOSISTEMA DE 4 SERVIDORES):
Las decisiones de diseño deben respetar estrictamente las responsabilidades de cada servidor:
- main-api: Orquestador y puerta de entrada.
- backend: Almacenamiento de datos de compras, publicaciones, información general de usuarios y warehouse.
- process-worker: Servidor para procesos pesados y manejo de colas de tareas (queues).
- ec-backend: Servidor con información de compras y usuarios, pero orientado a clientes.

2. REGLAS ESTRUCTURALES Y DE CÓDIGO:
- ARQUITECTURA: Respetar estrictamente la inyección de dependencias, decoradores y módulos de NestJS.
- CÓDIGO MODULAR: Cero código espagueti. Las funciones deben ser modulares, aplicar Clean Code y no modificar nada más allá de lo estrictamente solicitado.
- TIPADO ESTRICTO Y ZERO LINTER ERRORS: 
  * PROHIBIDO el uso de `any` (explícito o implícito). Usar tipos concretos o DTOs.
  * PROHIBIDO el uso de non-null assertions (`!`). Manejar la opcionalidad mediante Optional Chaining (`?.`), Nullish Coalescing (`??`) o validaciones explícitas con `if` / `assert`.
  * PROHIBIDO dejar variables, constantes, parámetros o imports sin usar. Si una variable es estrictamente necesaria pero no se consume, renombrarla con un guion bajo inicial (`_variable`).
  * El código resultante debe pasar la verificación de ESLint y TypeScript sin warnings ni errores.
- CIBERSEGURIDAD Y PROTECCIÓN DE ENDPOINTS (SEGURIDAD POR DISEÑO):
  * Todo endpoint nuevo o flujo refactorizado debe contar con validación estricta de inputs de entrada utilizando DTOs y `class-validator`/`class-transformer`.
  * Aplicar autenticación y autorización correspondiente utilizando los Guards nativos de NestJS según el contexto del endpoint y servidor.
  * Prevenir vulnerabilidades comunes (ej. inyecciones SQL/NoSQL en Prisma, exposición de PII, ataques de fuerza bruta).
  * Considerar e implementar Rate Limiting para endpoints públicos o expuestos a abusos.
- MANEJO DE EXCEPCIONES Y RESPUESTAS AL FRONTEND:
  * Prohibido silenciar errores con bloques catch vacíos.
  * LOGS INTERNOS: Utilizar el Logger nativo de NestJS para registrar el detalle técnico completo (stack traces, errores de DB o inyección de dependencias) exclusivamente en el servidor.
  * RESPUESTAS AL CLIENTE: Hacia el frontend, lanzar siempre excepciones HTTP estructuradas (`BadRequestException`, `NotFoundException`, etc.) con mensajes profesionales y amigables.
  * CERO FUGA DE DATOS: Bajo ninguna circunstancia se debe exponer información de infraestructura, librerías o código interno en el response. Los errores 500 (`InternalServerErrorException`) deben llegar al cliente con un mensaje genérico (ej. "Error interno del servidor, contacte a soporte"), mientras el detalle real queda en los logs del backend.
- RENDIMIENTO Y CONCURRENCIA: Implementar operaciones asíncronas de baja latencia preparadas para alta carga de usuarios.
